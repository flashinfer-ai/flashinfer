# CAKE training renames (#8928): migration from 0.7.3 and 0.7.4rc1

Issue #8928 gives every CAKE training family one naming scheme. The facade module is `flashinfer.cake_<op>_<mode>_train[_kcp]`, and its backend package is `flashinfer/experimental/cake/<module>/`. `<mode>` is `det` (run-to-run bitwise deterministic) or `nondet` (no run-to-run bitwise promise). Each family moves in its own rename PR or PRs; the PR columns below name them. This page maps the modules, names and backend directories of FlashInfer 0.7.3 and 0.7.4rc1 to their new names.

The mode is part of the name. No new entry takes `deterministic=`. The old names are removed without aliases, by the family PR or by an earlier PR that a row or a table note names. In 0.7.4rc1 several modules selected the mode with `deterministic: bool = True`. A call that kept the default ran deterministic programs, also in the modules that later became the `nondet` ones. Callers that kept the default move to the `det` module. `deterministic=False` callers move to the `nondet` module, except for the MoE entries that ignored the argument and for 0.7.4rc1 calls made while `torch.use_deterministic_algorithms(True)` was on (see "Calls that took `deterministic=`").

## Status and mode labels

PR column, and the PR after each name in the Use now column:

- `#N`: the PR that renames the family, or the PR that removed the old path. Each family is renamed in its own PR or PRs (mHC and mHC head share #8907; causal conv1d and LM head + loss rename `det` and `nondet` in separate PRs), and the renames are released together, so you migrate once. Names in a PR that has not merged yet can still change before it merges.
- `planned`: no PR has the new name yet. The new name is the #8928 target name, from the target table and naming rules in `docs/training_backend_names.md`.

Mode columns (0.7.3, 0.7.4rc1):

- `det`: deterministic programs only: run-to-run bitwise reproducible.
- `nondet`: programs that do not promise run-to-run bitwise results, with no deterministic route.
- `nondet, det by default`: the `nondet` programs ran only with `deterministic=False`. The default call ran deterministic programs, loaded by the directory itself or by its facade module. For a directory, the Note column of the Backend directories table says which.
- `det alias of <dir>`: no sources of its own. It re-exported the det package in `<dir>`.
- `-`: absent in that release. In a row marked "(as in 0.7.3)" or "(as in 0.7.4rc1)", `-` marks the release that the other row covers.

In column (Public names): the releases that shipped the old name. Names that existed only on main between releases are not listed.

Call forms in the Public names tables:

- `(default)`: a call that did not pass `deterministic=False`.
- `(..., deterministic=False)`: a call that passed `deterministic=False`. After a module or package name, `(deterministic=False calls)` means the calls of its entries that passed `deterministic=False`.
- `(Cake route)`: a call that ran the Cake backend (`backend="cake"`, the default in 0.7.3 and 0.7.4rc1).
- `{a, b}`: several names in one row. They map in order to the names in the New name cell. A single new name receives all of them.
- A name that keeps its spelling in the new module or package (for example the ALL_CAPS constants such as `ARCHES`) has no row of its own. The row of its module or package gives its new location.

## Calls that took `deterministic=`

| Old call (0.7.3 or 0.7.4rc1) | New call |
| --- | --- |
| an old entry called with the default, or with `deterministic=True` | the same entry of the family's `det` module |
| an old entry called with `deterministic=False`, with torch's deterministic mode off | the same entry of the family's `nondet` module |
| MoE: `cake_grouped_mm` or `cake_grouped_det_mm` of `flashinfer.grouped_mm`, `flashinfer.grouped_mm.cake`, `flashinfer.experimental.cake_moe_grouped_gemm` or `flashinfer.experimental.cake_moe_grouped_det_gemm`, or `CakeGroupedMm.apply` / `CakeGroupedDetMm.apply` of the two `flashinfer.experimental` packages, with any `deterministic` value | `flashinfer.cake_moe_grouped_gemm_det_train.cake_moe_grouped_gemm_det` or `flashinfer.cake_moe_grouped_gemm_det_train.CakeMoEGroupedGemmDetFunction`: these old entries ran the det programs for every value |
| a 0.7.4rc1 entry called with `deterministic=False` while `torch.use_deterministic_algorithms(True)` was on | the same entry of the family's `det` module. In this case `flashinfer.cake_kda_train`, `flashinfer.cake_kda_train_kcp`, `flashinfer.experimental.cake.cake_mhc_train`, `flashinfer.experimental.cake.cake_causal_conv1d_train`, `flashinfer.cake_causal_conv1d_train_kcp`, `flashinfer.cake_gdn_train_kcp`, `flashinfer.chunked_lm_head` and `flashinfer.experimental.cake.grouped_mm` ran the `det` programs and warned once. Exception: `cake_grouped_mm(..., fuse_wgrad_accumulation=True)` of `flashinfer.experimental.cake.grouped_mm` warned and then raised `NotImplementedError`. `flashinfer.cake_rmsnorm_train` and `flashinfer.cake_rmsnorm_silu_gate_train` raised `RuntimeError`, or ran the `det` programs with `warn_only=True`. Their support queries (`is_cake_rmsnorm_train_supported`, `is_cake_rmsnorm_silu_gate_train_supported`) and `cake_rmsnorm_silu_gate_train_reset_workspace` did not depend on that mode: their `deterministic=False` calls map to the `nondet` entries. The package `flashinfer.experimental.cake.cake_moe_grouped_gemm`, called directly, did not fall back: its weight-gradient entries raised PyTorch's non-determinism alert (`RuntimeError`, or a `UserWarning` with `warn_only=True`). Its calls map to `flashinfer.cake_moe_grouped_gemm_nondet_train`. The `nondet` modules never fall back to `det`. |
| any new entry called with `deterministic=` | `TypeError`: no new entry has the parameter |
| an old module, old name or old backend path in the tables below | fails at import; there are no aliases. Exception: `flashinfer.dsa_indexer` and its `dsa_indexer_det_topk` stay for `backend="sm120"`; a Cake-route call raises when it runs: `ValueError` for `backend="cake"`, `TypeError` without `backend=`. |
