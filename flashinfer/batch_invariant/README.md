# Batch-invariant kernels (`flashinfer.batch_invariant`)

`flashinfer.batch_invariant` provides deterministic, batch-invariant implementations of FlashInfer operators, selected
with the keyword `batch_invariant=True` on the operator's public API. The kernels are generated by an
engine that fixes the order of every floating-point reduction and the exact instructions the kernels issue, tensor-core
instructions included; the reduction orders are proved in Lean and the generated kernels are checked bit for bit on the
device.

## The guarantee

With `batch_invariant=True` an output's bits depend on the input values and the fixed dimensions alone:

| | Property | Meaning |
|---|---|---|
| R1 | Run-to-run determinism | same inputs, same path: same bits, across processes, streams and CUDA-graph replay |
| R2 | Batch invariance | a row's bits do not depend on batch size, padding, position, neighbours or SM count |
| R3 | Configuration agreement | every configuration the dispatcher or the autotuner may pick gives the same bits |
| R4 | Cross-path agreement | the members of one class (for example the operand layouts an operator accepts, or two implementations of one reduction) give the same bits |

Each class has one fixed dataflow, named and hashed into a **fingerprint**; `flashinfer.batch_invariant.fingerprint(op,
**dims)` returns it, scoped to (fingerprint, FlashInfer version, architecture). Bitwise equality is the acceptance
criterion of every test of the mode (`tests/gemm/test_batch_invariant_mm_bf16.py`, `tests/gemm/test_batch_invariant_bmm_fp8.py`, `tests/gemm/test_batch_invariant_mm_mxfp8.py`, `tests/gemm/test_batch_invariant_mm_fp4.py`,
`tests/batch_invariant/test_lean.py`).

## The dispatcher and the launch grid

Each class has an enumerated configuration space (tile, cluster shape, 2-CTA pairing, raster order, swizzle band, chunk
fold); every record computes the class, so the choice among them moves time only (R3). `gemm/batch_invariant/heuristic.py`
orders the records for a shape, layout, format and part by a per-tile roofline estimate: waves of tiles over the part's
co-resident cluster capacity, each the slower of its MMA and its L2-to-SMEM traffic per k-step, the aggregate L2 bound,
the operands' HBM bytes plus a share of the bytes the scheduler's tile order fetches again (which operand panels stay
resident in the L2 across a swizzle band), the epilogue and the split's fixup, with a few empirical constants shared by
every part and format (none fitted per part). The first record is the default; `autotune(True)` profiles the first ten
(the best five, each with its raster twin) and keeps the bits by construction. The persistent grid is the device's
co-resident cluster count for the record's cluster shape (the CuTe DSL's GPC-aware occupancy query, asked once per
device): a launch parameter that decides which CTA computes which tile and never a bit. The heuristic takes the device's
queried capacity and L2 size once the API has recorded them, else the family's nominal table; the generated Lean dispatch
cases are the nominal parts' (`nominal=True`).

## How to check the proofs

`lean/` holds one Lean 4 project (no Mathlib). Per class it models the dataflow as terms over opaque, correctly rounded
primitives (one opaque tensor-core step per operand format: `mma16` for bf16, `mma32` for the fp8 formats, so the fp8
classes are different terms from the bf16 class even at equal K) and proves that every implementation of the class the
kernels may run (for example a split reduction with its index-addressed workspace, or a pipelined loop with any stage
count) is the class's term, including its epilogue chain, and the launch-model statements of R1 and R2; an elementwise
postfix of the chain such as the bias lifts every identity by congruence, and the biased and the unbiased chain are proved
to be different terms. The model gives a configuration no way to reach an output element (R3 is immediate in it, and
is instantiated on the whole enumerated configuration space); that the kernel realises the model is what the engine's
lowering trace and the GPU configuration-agreement tests establish. What Lean cannot state is the hardware hypothesis that the instruction variants a
configuration space selects compute the same per-element function; the GPU configuration-agreement tests check it bit
for bit. A second hardware hypothesis of the block-scaled classes: the block-scaled step gives the same bits with its two operands exchanged, which the swapped decode records (`swap_ab`: the weights as the kernel's A, the tokens as its B) rely on; the dispatcher takes those records up to 64 rows and the dense records above, so the rows of a 64-row and a 65-row call are compared bit for bit in `test_batch_invariance_along_rows` of the mxfp8 and fp4 suites (M = 63, 64, 65 among the row counts), and every swapped record against the dense one in `test_swapped_decode_records_compute_the_class`, on each part.

`Cases.lean` is generated from the Python specification and engine (`python -m flashinfer.batch_invariant.lean_cases`):
the Lean model reproduces the Python S-expressions node for node, re-derives the dispatchers' shape rules and checks
every record of a configuration space and every dispatcher pick against the class's constraints. The device-free test
`tests/batch_invariant/test_lean.py` byte-compares the committed file; its `lake` steps run when the toolchain is
installed.

Trust statement: **Lean's standard axioms (`propext`, `Classical.choice`, `Quot.sound`), plus `Lean.ofReduceBool` for the
named exhaustive checks listed in `lean/Axioms.lean`** (the configuration-space and dispatcher-membership checks over
hundreds of records per format, decided by `native_decide`; every other generated case is kernel `decide`). `Lean.ofReduceBool` trusts the compiled evaluator for
those closed Boolean terms; `lake exe axioms` enforces exactly this list and fails on any `sorry`.

```bash
curl -sSfL https://raw.githubusercontent.com/leanprover/elan/master/elan-init.sh | sh -s -- -y --default-toolchain none
export PATH="$HOME/.elan/bin:$PATH"            # the pinned toolchain is lean/lean-toolchain (leanprover/lean4:v4.15.0)
cd flashinfer/batch_invariant/lean
lake build && lake build conformance axioms    # ~1 min cold
lake exe conformance                           # the Lean model's terms for the generated cases
lake exe axioms                                # the axiom policy: 0 with sorry, 0 violations
```

The Lean steps are not run in CI. The `lean/` directory is part of the repository only: it has no `__init__.py` and
no package data entry, so no `.lean` file is in the wheel.

## Quantization

The quantizers have no cross-row reduction: a block's scale and codes depend on that block alone (per-token NVFP4: on
its row, whose amax sets the row's global scale), so FlashInfer's own kernels are already batch invariant in the R1 / R2
sense. What `batch_invariant=True` adds is a specified, fingerprinted
dataflow (R3 across the enumerated configurations, R4 across the scale-factor layouts and the input dtypes that widen
exactly), a closed-form dispatcher whose every pick is a member of one enumerated space, and the exact CPU model and Lean
statements of the chains. The flag requires `backend="auto"` (the default, which runs the CUDA kernel without the flag) on the
three operators and on `fp4_quantize`, their shared entry point.

| API | Classes and fingerprint | Numerics | Supported inputs |
|---|---|---|---|
| `mxfp8_quantize` | `mxfp8.quant`; `fingerprint("mxfp8_quantize")` (no dimension: one specification per format) | TransformerEngine's MXFP8 chain: block amax as a pairwise `max` tree over `abs`, the UE8M0 scale `cvt.rp.satfinite.ue8m0(amax * fp32(1/448))`, the exact inverse `2^(127 - e8)` at every byte, the elements `cvt.rn.satfinite.e4m3(mul.rn(x, inv))`. The corners are part of the chain: a block whose amax is below `448 * 2^-127` (scale byte 0) keeps its values under the exact inverse, a NaN element gives `0x7F`, `-inf` gives `-448` | bf16 / f16 / fp32 inputs of shape `(..., K)`, `K` a multiple of 32 and rows of at most 128 KiB, `alignment` padding; the 128x4, 8x4 and linear scale layouts (placements of the store: the same bytes); SM100 / SM103 / SM107 |
| `mxfp4_quantize` | `mxfp4.quant`; `fingerprint("mxfp4_quantize")` | TransformerEngine's MXFP4 recipe: the same chain carried to e2m1 (`fp32(1/6)`, `cvt.rn.satfinite.e2m1`; the tiny-block threshold `6 * 2^-127`) | as above (`K` a multiple of 32); the three layouts |
| `nvfp4_quantize` | per-tensor `nvfp4.quant` (`fingerprint("nvfp4_quantize")`), per-token `nvfp4.quant.pertoken` (`fingerprint("nvfp4_quantize_per_token", K=)`: the row amax tree spans the row, so the row length is a dimension) | TransformerEngine's NVFP4 recipe with every operation correctly rounded or exact: the block amax as a pairwise `max` tree over `abs`, `sf = cvt.rn.satfinite.e4m3(amax * (gs * fp32(1/6)))`, `inv = fmin(1 / (sf * (1 / gs)), FLT_MAX)` with correctly rounded divisions, the elements `cvt.rn.satfinite.e2m1(mul.rn(x, inv))`; per token the row's global scale `gs = nzor(fmin((1 / gs_inv) / ramax, FLT_MAX), 1)` (`ramax` the row amax tree; `FLT_MAX` for an all-zero row) and the returned per-token scale `1 / gs` | bf16 / f16 / fp32 inputs, `K` a multiple of 16; the per-tensor global scale an input (a float or a 1-element fp32 tensor), the per-token inverse base scale; the three layouts and `do_shuffle` (FlashInfer's own host shuffles applied to the class's linear-layout bytes; a multiple of 32 rows, as FlashInfer's shuffle requires); `sf_vec_size` 16; no 4over6 recipe, no fp8 input, no `expanded_idx_to_permuted_idx`, no `out_scale`; SM100 / SM103 / SM107 |

The chains are the contract: named by the fingerprints, stated in Lean and checked against their exact CPU model, they are
what the classes promise with respect to TransformerEngine's recipes. FlashInfer's other quantizer backends are not a
reference for the classes and nothing is promised relative to them: their numerics may change within their own tolerances.

The quantizers' dispatcher is a closed form of `(M, K, element bytes, SM count, layout)`: one configuration per call, no
autotuning (`quantization/mx_schedule.py`, `quantization/nvfp4_schedule.py`), fitted on CUPTI sweeps of both parts.
The Lean model (`lean/BIKernels/Canon.lean`, `Semantics.lean`, `MXQuant.lean`, `Quant.lean`) states the engine's reduction
orders and the chains; `lake exe quantconformance` prints its terms for the generated cases
(`lean/BIKernels/QuantCases.lean`, rendered by `quantization/lean_cases.py`), which the device-free test
`tests/batch_invariant/test_quant_lean.py` compares with the Python specification. Tests:
`tests/quantization/test_batch_invariant_mx_quantize.py` (both MX formats) and `test_batch_invariant_nvfp4_quantize.py`.

## Sampling

`flashinfer.sampling.softmax(logits, temperature, batch_invariant=True[, out_dtype=])` and the new entries
`flashinfer.sampling.log_softmax(logits, temperature)`, `flashinfer.sampling.log_probs(logits, token_ids,
temperature, return_lse=, return_entropy=)` and `flashinfer.sampling.entropy(logits, temperature)` run one class,
`lse.row`: the row maximum `m` and the sum `s` of the exponentials as the
engine's canonical trees over the vocabulary (an 8-element fold per slot, pairwise over the blocks of 256 elements,
pairwise over the 32 lanes: a function of the vocabulary alone, never of the batch, the configuration or the device),
and fixed chains over them. The operator's own softmax selects its reduction path by batch size, so a row's bits there
depend on the batch; the class is what the mode promises instead.

| API | Class and fingerprint | Numerics | Supported inputs |
|---|---|---|---|
| `softmax(..., batch_invariant=True, out_dtype=)` | `lse.row`; `fingerprint("softmax", N=, dtype=, temperature=[, out_dtype=])` (the vocabulary, the input dtype and whether a temperature enters the scale are the specification's dimensions; `out_dtype=torch.float32` names the fp32 input's specification: the leaves of a 16-bit input are its exact widenings, so only the output conversion differs) | `c = log2(e)` or `div.rn(log2(e), T)`; `z_j = mul.rn(add.rn(x_j, neg(m)), c)`; `e_j = ex2.approx.ftz(z_j)`; `s` the `add.rn` tree over the `e_j`; `p_j = cvt.rn(mul.rn(e_j, div.rn(1, s)))` in the input dtype, or `mul.rn(e_j, div.rn(1, s))` itself with `out_dtype=torch.float32`. `m` is the `max.f32` tree (a NaN operand yields the other; a NaN logit then propagates through the sum), a `-inf` logit weighs `+0` | bf16 / f16 / fp32 logits `(..., N)`, any `N`; temperature `None`, a positive scalar, or one per row (f16 / bf16 / f32 / f64, the last rounded to f32); same-dtype or fp32 output; `enable_pdl`; SM100 / SM103 / SM107 |
| `log_softmax(logits, temperature)` | the same class and fingerprint (`fingerprint("log_softmax", ...)`) | the row `logp_j = mul.rn(add.rn(z_j, neg(lg2.approx.ftz(s))), ln 2)` in fp32, shape `logits.shape` | as above; this entry has no non-invariant implementation (`batch_invariant=False` raises) |
| `log_probs(logits, token_ids, temperature, return_lse=, return_entropy=)` | the same class and fingerprint (`fingerprint("log_probs", ...)`); with `return_entropy` also the entropy member below (its own fingerprint) | the log-softmax row above gathered at the row's token ids (NaN for an id outside `[0, N)`), with `return_lse` the row's `lse = mul.rn(add.rn(mul.rn(m, c), lg2.approx.ftz(s)), ln 2)`, with `return_entropy` the row's entropy below (one launch; the tuple is `logp`, then `lse`, then `entropy` as asked); fp32 outputs of the ids' shape / `logits.shape[:-1]` | as above; `token_ids` int32 / int64 of shape `logits.shape[:-1]` (one id per row) or `logits.shape[:-1] + (K,)` (`K` ids per row in one launch); `batch_invariant=False` raises |
| `entropy(logits, temperature)` | the entropy member of `lse.row`; `fingerprint("entropy", N=, dtype=, temperature=)` (its own: the member's tree and chain; the class's other fingerprints do not move) | a third tree `W` with the digits of `s` over `w_j = ZSEL(e_j, mul.rn(e_j, z_j))`, `ZSEL(e, p) = +0 if e == 0 else p` an exact select (`setp.eq` + `selp`: a `-inf` logit's weight-less NaN product becomes the additive identity `+0`, the identity the padded elements feed; a NaN weight passes); `H = mul.rn(add.rn(lg2.approx.ftz(s), neg(div.rn(W, s))), ln 2)`, the natural entropy `-sum p ln p` of `softmax(x / T)` (`p_j = e_j / s`, `ln p_j = ln 2 (z_j - lg2 s)`); `W` rides the sum pass (no third pass); fp32 of shape `logits.shape[:-1]`; a one-hot row is exactly `0`, an all-`-inf` or NaN row is NaN | as above; `batch_invariant=False` raises |
| `log_probs_tp_partials(...)`, `log_probs_tp_merge(...)`, `log_probs_tp(...)`, `log_softmax_tp(...)`, `softmax_tp(...)` | the same class and fingerprint, on a vocabulary shard of a tensor-parallel rank | the tensor-parallel protocol of the class: two rounds of the class's own sub-trees and their merge, the sharded outputs from the merged statistics -- the subsection "The tensor-parallel protocol" below | the shard as `(..., hi - lo)`; the ranks' shards a contiguous tiling of `[0, N)` on multiples of 8 columns |

The entropy is what the RL trainers form next to the token log-probability on the same logits (verl's `entropy_from_logits`,
Miles' `_VocabParallelEntropy`, NeMo RL's `ChunkedDistributedEntropy`: the entropy of `softmax(x / T)`), so the member
produces it from the same trees in the same launch as `log_probs`; the two are the same bits whether asked together or
separately. Against those trainers' torch formulas (`-(softmax * log_softmax).sum`, `logsumexp - (softmax * x).sum`, on
the fp32 upcast) the member runs at 0.04-0.38 of the best one's time over vocabularies 32768 .. 262144 x 1 .. 4096 rows on
both the Rubin NVL8 (SM107) and the B200 (SM100); inside the class it costs 1.1-1.6x the class's `logsumexp` (the pair
pass is issue-bound: the sum pass gains a `mul`, the select and an `add` per element).

A row view into a wider tensor (the `[..., :vocab]` slice of a padded lm_head) whose row stride is a multiple of 16 bytes
is read in place; other views are copied first (a placement). For a sampler and a trainer to agree bit for bit they must
call with the same arguments: raw logits and the temperature (the class scales inside its chain), or identically
pre-scaled logits and `temperature=None`; a greedy row's temperature of 0 is `None`.

`ex2.approx.ftz.f32` and `lg2.approx.ftz.f32` are the class's two opaque primitives: deterministic per architecture,
pinned as inline PTX in the kernel, and tabulated on the device for the exact CPU model (`sampling/mufu_device.py`).
Everything else is a correctly rounded `.rn` operation or exact. The chains are the contract, named by the
fingerprints, stated in Lean and checked against the exact CPU model (`sampling/reference.py`); nothing is promised
relative to the operator's other softmax kernels or to torch.

The kernel (`sampling/kernel.py`) runs the two trees as the engine's plan over a placement of the configuration space
(`sampling/schedule.py`: 32 .. 1024 threads per row, rows per CTA, the vector width, fragments kept in registers /
re-read from L2 / staged in shared memory, and clusters of 2 .. 16 CTAs per row whose per-lane partials cross the
cluster through distributed shared memory), then writes the requested outputs in a third pass; the vocabulary is a
runtime argument (one kernel per power-of-two block count; elements beyond the row read `-inf`, the identity of both
trees). The dispatcher is a closed form of `(N, M, element bytes, SM count, which outputs)` with empirical constants
(`default_config`): clusters when there are fewer rows than SMs, one CTA per 64 / 128 KB of the row otherwise; every
pick is a member of the enumerated space and every member computes the class (the configuration-agreement tests).

The Lean model (`lean/BIKernels/Sampling.lean`) instantiates the engine's invariance theorems on the three trees
(`max_invariance`, `sum_invariance`, `w_invariance`), carries them through the chains (`lse_end_to_end` /
`entropy_end_to_end`: for every valid placement and unit the kernel's probabilities, log-softmax elements, `lse` and
entropy -- the last over the kernel's own three trees -- are the spec's up to the commutativity the engine normalises,
hence `lse_bits_equal` / `entropy_bits_equal` under any commutative interpretation), and states the `-inf`-padded bucket
kernel bit for bit under the restricted identity hypotheses the spec's digits claim (`max_padded_bits`, `sum_padded_bits`,
`w_padded_bits`; `wTerm_neg_inf_identity` derives the entropy tree's hypothesis from `ex2(z(-inf)) = +0` and
`ZSEL(+0, p) = +0`). The `Term` language gains the named opaque binary primitive `opq2` (`ZSEL` is `opq2 "zsel"`).
`lake exe samplingconformance` prints its terms for the generated cases (`lean/BIKernels/SamplingCases.lean`,
rendered by `sampling/lean_cases.py`; kernel `decide` only), which the device-free test
`tests/batch_invariant/test_sampling_lean.py` compares with the Python specification. Tests:
`tests/utils/test_batch_invariant_sampling.py`.

### The tensor-parallel protocol

The RL trainers hold the vocabulary sharded over the tensor-parallel ranks and form the token log-probability from a
per-rank maximum and a per-rank `exp(x - m)` sum joined by two all-reduces (Megatron's `vocab_parallel_cross_entropy`,
NeMo RL's distributed log-softmax, Miles and verl under Megatron); that dataflow rounds differently from the full row,
so their parity modes gather the whole row. The class's trees are defined on the global vocabulary, so a rank holding
the slot-aligned shard `[lo, hi)` (multiples of 8; the last shard may end at `N`) can compute every **maximal complete
sub-tree** of the row trees inside its shard, and the ranks' partials merged by the fixed upper part of the tree are the
global term node for node. The entries, on every rank:

| API | Class and fingerprint | Numerics | Supported inputs |
|---|---|---|---|
| `log_probs_tp_partials(shard_logits, shard_start, shard_end, vocab_size, temperature, m=None, width=)` | `lse.row`; `fingerprint("log_probs", N=, dtype=, temperature=)` -- the partials are the class's own sub-trees, the wire format (`sampling/shards.py: ShardLayout`) a layout, not a class | round 1 (`m=None`): per lane of the row tree the dyadic decomposition of the lane's in-shard block range, each piece the `max.f32` sub-tree at that position, concatenated lane by lane (`P_r` fp32 per row: 104..264 for the eight shards of 152064; a function of `(lo, hi, N)` only); round 2 (`m` the merged maximum): the same pieces of the `add.rn` tree over `ex2.approx.ftz(mul.rn(add.rn(x, neg(m)), c))` | the shard as `(..., hi - lo)` bf16 / f16 / fp32; `width >= P_r` pads to the all-gather's common width; SM100 / SM103 / SM107 |

| `log_softmax_tp(...)`, `softmax_tp(...)` | the same | the shard's columns of the log-softmax / softmax row from `(m, s)`: the full row's `[..., lo:hi]` bit for bit | as above |

**Two rounds, by necessity.** The class's sum tree is over `e_j = ex2((x_j - m) c)` with the *global* maximum. A
one-round protocol exchanging per-rank `(m_r, s_r)` and merging them with the online-softmax rescale
`s = sum_r s_r ex2((m_r - m) c)` is a different term (a different rounding sequence: `ex2(a) ex2(b)` is not `ex2(a + b)`
in binary32, and `x - m_r` is not `x - m`), i.e. a different class, never bit-identical to the TP = 1 row; the test
`test_online_merge_is_not_the_class` pins the structural inequality. So: max partials -> all-gather -> merge -> `m`;
sum partials over `ex2((x - m) c)` -> all-gather -> merge -> `s`; the sharded outputs from `(m, s)`. The collectives are
the trainer's (the API takes the gathered tensor); a rank sends `2 x 4 Pmax` bytes per row (256 B at 32768 / 262144 at
any TP, 1.6-2.6 KB at 128256 / 152064) against the 2 x 4 B of the two-all-reduce protocol and the `2 N` bytes of a full
row gather (304 KB at 152064); `tp_api.lse_row_tp_stats` runs the two rounds given the trainer's all-gather.

The partials kernel (`sampling/tp_kernel.py`) covers the shard's block span with `kpw W C` blocks aligned to the CTA
unit, runs the engine's slot fold (`canon.init_state`), forms the pieces as the adjacent-pairs trees over the thread's
chunk, the warps' chunk roots (the engine's warp exchange) and the CTAs' roots (the cluster exchange), and stores each
candidate at its layout slot when it is a maximal in-shard sub-tree; its configuration space (`sampling/tp_schedule.py`)
is a placement space (every member writes the identical tensor; the vector width follows the shard tensor's alignment,
a view of a wider tensor or the last shard of a vocabulary that is not a multiple of 8 forcing a narrow one). The merge
kernel stages the CTA's rows' partials in shared memory, gives every tree lane its own warp (the lane class's
straight-line program -- `shards.merge_ops`, the merge recursion linearised -- is then a warp-uniform branch) and runs
the engine's lane butterfly per row; a tiling with one lane class keeps the lane-mapped form.

The Lean model (`lean/BIKernels/SamplingTP.lean`) proves the merge: `mergeNode_eq_subtree` (rebuilding a block tree from
any family of given nodes that carry the tree's own sub-trees yields the tree, provided every present leaf lies under a
given node), `tiling_cover` (for shards tiling `[0, N)` on slot boundaries every present block of every lane lies under a
piece of the rank holding it), **`tpMax_eq_specMax` / `tpSum_eq_specSum` / `tp_protocol` / `tpOutputs_eq_specOutputs`**:
the merge of the ranks' pieces, then the lane tree, *is* the spec's maximum / sum term, round 2 over the merged maximum
is `specSumOfMax`, and every rank's outputs are the spec's -- term identities, so bitwise equality needs no commutativity
assumption; `piece_via_units` (a piece formed over an aligned group of chunk roots is the sub-tree). The generated cases
print the merged maximum and sum of three toy tilings and a shard's piece terms, and the production layouts' piece
tables (32000 / 8, 32768 / 2, 128256 / 8, 151936 / 4, 152064 / 8, 262144 / 8 and Megatron's padded 152576 / 8 and
129024 / 8) next to their tiling facts and the protocol theorem instantiated for any row and temperature; `lake exe samplingconformance` prints them and the device-free test compares them with
Python's. Tests: `tests/utils/test_batch_invariant_sampling_tp.py` (device-free: the layout equals the maximal
sub-trees, the partials program traced over every unit of every configuration stores exactly the layout's pieces as the
canonical sub-tree terms, the merge program rebuilds the row term; on a device: TP 1 / 2 / 4 / 8 of the production
vocabularies and Megatron's padded shards bit-identical to the TP = 1 kernel and the exact model, every sharded output
equal to the full row's, whole-space agreement of the partials tensor, batch invariance per shard, masked / NaN / inf
rows, a partial last slot, empty shards, M = 0, graph replay, the `+0` filler).

Measured (CUPTI kernel time of one rank's five kernels, cold L2, bf16, the sandbox's `bench_sampling.py --ops
log_probs_tp{2,4,8}`): at M = 4096 a TP-8 rank finishes in 1.8-4.7x (Vera Rubin, SM107) / 2.3-5.0x (B200, SM100) less
time than one device needs for the whole row (the two shard reads against the full-row kernel's single
register-resident pass: the ideal is TP / 2) and 8-33x faster than the trainers' per-rank max + exp-sum dataflow in
torch; at M <= 64 the five kernel floors (~2-4 us each) cost 10-26 us against a 4-8 us full row.
