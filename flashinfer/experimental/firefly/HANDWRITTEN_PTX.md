# Hand-written PTX: reasons, evidence, and how to re-check

This file records the hand-written PTX in the kernels of this directory, and why each instance cannot use a CuTeDSL interface. The places where an interface replaces hand-written PTX are also listed here, with notes on what to watch for when using the interface, so that they can be re-checked (for example after a CuTeDSL upgrade).

**Rule**: use CuTeDSL interfaces by default, including `cute`, `cute.arch`, `cute.math`, `cutlass.experimental.primitives`, and NVVM dialect ops. Numerically, the only requirement is that the error stays within the precision of the data type. Hand-write PTX only when the code generated by an interface is wrong, or when the interface version is more than 1% slower than the hand-written one, and only with reproducible evidence; when the interface version is at most 1% slower (even with a small amount of extra spilling), use the interface. When adding hand-written PTX, add an entry to Section 1 and mark the code's docstring with the same id.

**Environment**: CuTeDSL 4.8.1 (nvidia-cutlass-dsl, cu13), ptxas from CUDA 13.4.3, B200 (sm_100a).

Under this rule:
- **P3 uses the interface**: the time is unchanged or slightly faster; see the table below.
- **P4 is used only for M < 2048**. M ≥ 2048 uses the pure-interface 8-column version, which is faster.
- **P1 and P2 are hand-written**: P1 is a correctness issue, P2 a performance issue (the interface version measured 0.4-2.8% slower).
- Places that need a specific instruction form (`div.full`, `ex2` without ftz, `fma(a, b, 0)`, e4m3/e2m1 conversions, etc.) all use interfaces that generate the same instruction (see Section 2); the code has no hand-written PTX for these.

**The following also use interfaces, with no hand-written PTX**:
- **256B L2 promotion for the token-major gate/up**: CuTe's TMA atom always encodes the descriptor with 128B, with no parameter to change it. Instead, at the start of the kernel the load warp copies the W and X descriptors into the CTA's own global slot with `cpasync.copy_tensormap`, modifies byte 10, goes through `cpasync.fence_tma_desc_release`/`fence_tma_desc_acquire`, and then uses this copy in `cute.copy(..., tma_desc_ptr=)`. The pointers are generated with `cutlass.tensor_utils.tensormap.TensorMapManager.get_tensormap_ptr`: the copy needs a gmem pointer, the TMA a generic pointer. These fence helpers are CuTeDSL's own inline asm internally and count as interfaces.
- **256B descriptors on the host side for the direct GEMM**: this is just a parameter of `cuTensorMapEncodeTiled`.
- **L2 prefetch and epilogue math**: the down GEMM's L2 prefetch (`GroupedGemm(l2_tiles=)`, `placement.l2_prefetch`) uses the NVVM dialect's `nvvm.cp_async_bulk_prefetch` (`cp.async.bulk.prefetch.L2.global`), with the pointer generated by `llvm.inttoptr`; the epilogue's row-scale prefetch uses only `cute.arch.load`/`store`; the token-major epilogue's SwiGLU uses `cute.arch.rcp_approx`. `cute.math.tanh(fastmath=True)` generates `tanh.approx.f32` (without fastmath it generates a precise, non-approximate instruction sequence).

**Bulk reduce for the long-batch fused finalize (interface)**: the token-major down epilogue issues one `cp.reduce.async.bulk.global.shared::cta.bulk_group.add.noftz.bf16` per row (`_epilogue_token_major_fused` in `gemm.py`). The NVVM dialect has only the non-tensor bulk copy (`nvvm.cp_async_bulk_global_shared_cta`) and the tensor form of reduce, but no non-tensor reduce; `cutlass.experimental.primitives.cp_reduce_async_bulk_global_shared_cta` does have one (internally it is CuTeDSL's own inline PTX, so it counts as an interface), and the code uses it. Compared with the same instruction written by hand, the PTX differs only in whether the byte count is an immediate or a register. The accompanying `cp.async.bulk.commit_group` / `wait_group.read` use `cute.arch.cp_async_bulk_commit_group` / `cp_async_bulk_wait_group(0, read=True)`.

**L2 cache policy for weight loads (no hand-written PTX)**:
- The grouped GEMM uses the CuTeDSL interface: `cute.copy(tma_atom, ..., cache_policy=Int64(EVICT_FIRST))` (`GroupedGemm(evict_weights=True)`), which generates `cp.async.bulk.tensor....L2::cache_hint`.
- The direct GEMM's TMA is the hand-written P1/P2 (`tma_load_if_lt` in `direct.py`) and carries no cache hint.
- The policy values are CUTLASS's `CacheHintSm90`: `EVICT_FIRST = 0x12F0000000000000`, `EVICT_NORMAL = 0x1000000000000000` (at the top of `gemm.py`).
- For usage, see `evict_weights` of `GroupedGemm` in `gemm.py`, and `moe.weight_evict`.

## 1. Hand-written PTX (3 kinds: P1, P2, and P4, which is used only for M < 2048)

| Id | Helper (location) | Why not an interface | Evidence | How to re-check |
|---|---|---|---|---|
| P1 | `setp.lt.s32 p, kk, K` plus `@p` in `expect_tx_if_lt` and `tma_load_if_lt` (`_load` in `direct.py`) | **Correctness**. Written in the DSL as `Int32(nk < K)`, the comparison is folded to the constant 1 by MLIR canonicalize inside the `if ki > 0` branch: it is `arith.cmpi` in the raw IR and becomes `%c1_i32` after canonicalize. The out-of-bounds TMA for k ≥ K is then issued as well and writes its OOB zero fill into stage 0, which collides with the epilogue borrowing stage 0 for its `stmatrix`/`ldmatrix` exchange; at M=3/4, groups of zeros occasionally appear in the output. It does not reproduce in a small kernel, and the root cause has not been found. The NVVM TMA op and the `mbarrier.arrive.expect_tx` op both have a predicate operand, but the predicate would still have to be computed in the DSL and could be folded in the same way, so they are not used. | Dump the raw IR and the post-canonicalize IR of the M=4 gate/up and compare them: the predicate is `arith.cmpi` in the former and `%c1_i32` in the latter | Change the comparison back to the DSL form and use `CUTE_DSL_KEEP=ir` to check whether the predicate becomes a constant after canonicalize; for M=3 and 4, run the correctness check several times with CUDA graph replay (new inputs on every replay) |
| P2 | `tma_load_if_lt`, `tcgen05_cp_x4_elect`, `tcgen05_mma_nvf4_elect` (`direct.py`) | **Performance**. These helpers issue the TMA, `tcgen05.cp`, MMA, and commit with `elect.sync`, a warp-0 test, and an `@p` predicate, without branching. `if warp == 0:` plus `with cute.arch.elect_one():` generates branches (52 BRA instructions in SASS) and is 2.8% slower at M=1. Neither the NVVM ops nor the primitives for tcgen05.cp, mma, and commit have a predicate operand, so an interface can only be used with a branch. | Time ratio (relative to the same reference kernel) of the branching version (`if warp == 0:` plus `elect_one`) vs. the current version in `direct.py`: 1.004-1.028 vs. 0.990-1.000 | Change back to the branching version and compare it with the current version at M=1, 2, 4, timed alternately in the same process |
| ~~P3~~ (**uses the interface**) | `st_global_v4` (`_epilogue_token_major` in `gemm.py`), written as `if row < row_end: cute.arch.store(...)` | Time ratios of the gate/up (token-major, PDL off) with the interface version: M=2048 0.982 (hand-written 0.984), 4096 1.001 (1.001), 8192 1.006 (1.007), 16384 1.009 (1.012). The interface version makes the token-major epilogue spill 4 bytes (1 extra STL and 1 extra LDL in SASS; ptxas reports an 8-byte stack); the result is the same whether the vector is assembled inside or outside the `if`. Per the rule at the top of this file, the interface is used. The predicated write-backs of the other three epilogues have no spill with interfaces; see Section 2. | Comparison of the PTX/SASS instruction statistics of the two versions of the M=4096 gate/up | Switch to `if` plus `cute.arch.store` and check for spills with `ptxas -v` |
| P4 | `_ld_words_pred` (`reduce.py`): a predicated 8-byte read that first zeroes the two words with `mov.b32 0`, then does `@p ld.global.v2.b32`, where p is `h < H`. **Used only for M < 2048** (`reduce_shape`) | **Performance**. Time ratios of the versions (relative to the same reference kernel, M=8 / 256 / 1024 / 2048 / 4096 / 8192 / 16384): P4 is 0.987 / 0.993 / 0.990 / 0.990 / 0.991 / 0.994 / 0.989; the pure-interface `cute.arch.load` b64 version is 1.220 / 1.055 / 1.029 / - / 1.165 / - / 1.158; pure interface with 8 columns per thread (16-byte reads, two `ld.global.v4` each for `inverse` and the weights) and 2 warps per CTA is 1.260 / 1.056 / 0.993 / 0.992 / 0.982 / 0.976 / 0.968; the same 8 columns with 4 warps and 1024 columns per CTA is 1.244 / 1.055 / 0.980 / 1.025 / 1.000 / 0.981 / 0.952. So M ≥ 2048 uses the 8-column version (4 warps for M ≥ 16384), and smaller M use P4. Reason: each ReduceRoutes thread reads 4 BF16 values from each of 8 routes. With interface reads, ptxas schedules only 6 of the 8 `LDG.E.64` before the first FFMA2, and the `inverse` index read of slot 5 is also moved after the FMAs, adding one more memory round trip. The P4 form keeps all 8 reads ahead of the computation. Time ratios at M=4096 and M=8 (relative to the same reference kernel): `cute.arch.load` (PTX `ld.global.b64`) 1.172 / 1.205; reading as `<4 x bf16>` (`ld.global.v4.b16`) 1.173 / 1.180; unpredicated asm `ld.global.v2.b32` 1.172 / 1.177; a DSL `if` with a pre-zeroed register tensor 1.044 / 1.205; **the P4 form 0.992 / 0.987**. Predicating only the index reads or only the weight reads has no effect (1.17). Another interface-only version, with `inverse` and the weights each changed to two `ld.global.v4`: 1.010 / 0.987. | Single-kernel time ratios of the versions in the previous column, and the positions of the LDGs in their SASS | Replace `_ld_words_pred` with `cute.arch.load`, look at the ReduceRoutes time at M=8 and 4096 with nsys, and check the position of LDG.E.64 in SASS |

**Two more places are not PTX, but do not go through the regular interfaces either**:
- `.maxnreg 128`: CuTeDSL's LaunchConfig has no such setting, so `CuTeDSL._generate_kernel_attrs` is patched to add `nvvm.maxnreg`; the code is at the top of `gemm.py` (`launch_regs`). The public alternative `launch(max_number_threads=[512, 1, 1], min_blocks_per_mp=1)` also fixes the count at 128 registers, but adds 7-8 instructions at the start of GroupedGemm and 8 bytes of spill in some kernels, and makes the ReLU2 long batch 1-3% slower; it serves only as a fallback, switched to automatically when the private method does not exist, its signature has changed, or it is no longer called (`gemm.MAXNREG_PATCH`).
- The direct GEMM's TMA descriptors are encoded on the host with `cuTensorMapEncodeTiled` and kept in global memory (`_encode`, `make_direct_descriptors`). The reason is that the TMA instructions of P1 and P2 are hand-written and cannot use CuTe's TMA atom. The kernel executes `prefetch.tensormap` first thing at its start; without the prefetch, M=1 is 8% slower.

## 2. Interfaces used in place of hand-written PTX

| PTX instruction | Interface used | Generated instruction | Notes |
|---|---|---|---|
| `div.full.f32` | `cute.math.div(a, b, full=True)` | `div.full.f32` | `/` generates `div.rn.f32`, which gives different results |
| `ex2.approx.f32` | `cute.math.exp2` | `ex2.approx.f32` | `cute.arch.exp2` generates `ex2.approx.ftz.f32` |
| `fma.rn.f32 d, a, b, 0` | `cute.math.fma(a, b, Float32(0.0))` | Same | The DSL expression `a * b + c` is contracted by LLVM into `fma.rn.f32`. When the multiply and the add need separate rounding, do not write them directly as an expression |
| `mul.f32`, `add.f32`, `neg.f32`, `sub.f32 0, x` | DSL operators | Same | Provided the product does not feed directly into an add (see the previous row); the code currently has no such combination |

| `cvt.rn.bf16x2.f32` | `.to(BFloat16)` on a 2-element TensorSSA | Same | |

## 3. Interface versions vs. hand-written versions

- For 28 GEMM configurations, the interface versions produce output bit-identical to the hand-written versions, and the time ratios (relative to the same reference kernel; single-kernel test, 300 replays, CUPTI) also match:

  | Group | Hand-written PTX | Interface |
  |---|---|---|
  | grouped, M=4096/2048 | 0.995-1.009 | 0.991-1.008 |
  | grouped, M=1024/512 (PDL) | 0.970-0.989 | 0.963-0.985 |
  | grouped, M=8-256 (BM 16/32) | 0.963-0.996 | 0.964-0.993 |
  | direct, M=1-4 | 0.973-1.000 | 0.971-1.006 |

  The direct M=2 gate/up measured 0.985 and 1.009 on two GPUs with 2000 replays each. This item by itself fluctuates by ±1%, and its SASS instruction statistics are the same as the hand-written version's.
- The interface versions use the same number of registers as the hand-written versions, and both have a 0-byte stack (`ptxas -v`).
- SASS instruction statistics: the counts of floating-point, smem, TMEM, and MMA instructions are the same; the only differences are in integer and branch instructions, and in the form of the TMA (the interface version uses a 3D box and needs no prefetch; the hand-written version uses a 5D box).

## 4. How to re-check

- After upgrading CuTeDSL, check the instructions actually generated by each interface in Section 2 (including the forms that are rejected and the block16 mapping error), and compare them with the results from CuTeDSL 4.8.1. Then confirm that the `.maxnreg` patch still works: `gemm.MAXNREG_PATCH` is True after import and still True after a GroupedGemm has been compiled (False means it has fallen back to the public form; see the end of Section 1). The P1 folding does not reproduce in a small kernel and must be checked separately as described in Section 1.
- Run the correctness checks on all configurations (including CUDA graph replay with new inputs on every replay); when switching to an interface does not change the math, also compare the output bit for bit with the output from before the switch. Timing: compare the two versions timed alternately in the same process.
- Compare the PTX/SASS instruction statistics and register counts of the two PTX versions; dump the PTX with `CUTE_DSL_KEEP=ptx CUTE_DSL_DUMP_DIR=<dir>`.
