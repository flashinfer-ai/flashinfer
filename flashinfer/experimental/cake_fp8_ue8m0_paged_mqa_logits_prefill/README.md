# Cake FP8 paged MQA prefill logits over UE8M0-scaled keys (SM103, SM107)

Owner: @jdebache · Tracking issue: Mistral Large 4 · Status: experimental, JIT-only.
Tested on a Rubin GPU (SM107, 200 SMs) and a GB300 (SM103, 152 SMs).

Experimental backend of `flashinfer.attn_scores.fp8_ue8m0_paged_mqa_logits_prefill`:
the DSA indexer prefill logits over an FP8 paged key cache whose per-token
scales are UE8M0 exponents (the indexer cache vLLM writes on SM100-family GPUs),
for the 32-head x 128 indexer geometry. It is the prefill counterpart of
`fp8_ue8m0_paged_mqa_logits_decode`
(`../cake_fp8_ue8m0_paged_mqa_logits_decode/`): every new token of every
request in a step is scored against the keys it sees, a causal staircase, in
one launch, reading the paged cache directly (no key gather) and writing FP32
scores (no upcast). Calling the API is the opt-in (it warns once
with `ExperimentalWarning`); it takes part in no automatic backend selection.

## Entry points

```python
from flashinfer.attn_scores import (
    fp8_ue8m0_paged_mqa_logits_prefill,
    plan_fp8_ue8m0_paged_mqa_logits_prefill,
)

# Once per step, from host values: request i's rows are rows
# [row_offsets[i], row_offsets[i] + row_counts[i]) of q, weights and the output,
# and its row j sees keys 0 .. prefixes[i] + j of block-table row i.
work = plan_fp8_ue8m0_paged_mqa_logits_prefill(
    row_offsets, row_counts, prefixes, device
)

# Per layer:
logits = fp8_ue8m0_paged_mqa_logits_prefill(
    q,             # [rows >= 8, 32, 128] float8_e4m3fn, contiguous
    kv_fused,      # [num_blocks, 64, 1, 132] uint8
    weights,       # [rows, 32] float32
    block_tables,  # [requests, width] int32, unit column stride, any row stride
    work,
    out=None,      # optional float32 [>= work.rows, >= work.max_len], contiguous
)                  # -> out; allocated as [work.rows, round_up(work.max_len, 4)]
```

Row `r` (request `i`'s row `j`) scores key `k <= prefixes[i] + j` as

```
2^(e_k - 127) * sum_h weights[r, h] * relu(q[r, h, :] . key_k)
```

in request-local positions, the layout `flashinfer.topk_varlen` gvr_2 reads in
its windowed (prefill) mode. Nothing past a row's visible keys is written. The
summation order is the decode kernel's, so a request's rows taken four at a
time match `fp8_ue8m0_paged_mqa_logits_decode` with next_n = 4 bit for bit.
The plan costs a NumPy pass and one pinned host-to-device copy: build it once
per step and reuse it for every layer. The copy runs on the stream that is
current when planning, and the calls do not wait for it: make them on that
stream, or make their stream wait for it first. The plan's copy makes the call
unsuited to CUDA-graph capture; prefill runs eagerly.

## Kernel

Work items are 8 consecutive rows of one request and a segment of its 128-key
tiles. The planner cuts tiles into segments so that there are about 32 items
per SM (at least 16 tiles each), ordered request by request and segment by
segment so that CTAs running together read the same keys. One persistent CTA
per SM takes items `c, c + grid, ...`. Roles:

- a load warp: per item, a TMA of the 8 rows' Q (8 x 32 x 128 FP8) and FP32
  weights (2 stages); per tile, the two pages' 3-D value boxes and 2-D scale
  boxes (six stages);
- two MMA warps, one per math warpgroup: `tcgen05` FP8 MMAs
  `D[128 keys, 4 rows x 32 heads] = K . Q^T`, K = 32, into that warpgroup's
  two TMEM slots;
- a scales warp: each tile's UE8M0 exponents to FP32 scales in a ring of its
  own, so that the math warps never read a stage that TMA refills (that read
  would need a proxy fence, which would also wait for their global stores);
- two math warpgroups, rows 0-3 and 4-7 of the item over the same keys: each
  key's TMEM row reduced to `sum_h w_h relu(acc_h)` in packed f32x2 FMAs,
  times the key's scale, stored as FP32 for the visible keys.

Each key is read once per 8 rows.

## Layout of this package

- `backend.py`: the planner (`plan`, `plan_work`), the input checks, the JIT
  load and the launch: the TMA descriptor dimensions and 16-byte strides the
  generated launcher takes, and the grid. On load it checks that the
  program's launcher takes exactly the parameters it binds.
- `../cake_fp8_ue8m0_paged_mqa_logits_common/`: shared with the decode
  backend: the supported architectures, the generated-program loader and
  launcher check, and the launch-device guard.
- `csrc/dsa_indexer_prefill_logits_{sm_103a,sm_107a}.py`: CuTe DSL programs
  generated by Cake (loom's CuTe DSL backend). Do not edit them. They import
  only `cutlass` (nvidia-cutlass-dsl) and `cuda.bindings`, so neither loom nor
  Cake is needed at runtime. The two differ only in the target they name. They
  are compiled on first use and cached by `flashinfer.jit.cute_dsl_core`.

Regeneration requires the separately maintained Weave kernel sources and
CAKE exporter; neither is a runtime dependency of this package. From that
source checkout, invoke its prefill export entry point with
`<flashinfer>/flashinfer/experimental/cake_fp8_ue8m0_paged_mqa_logits_prefill/csrc`
as the output directory, and set `CAKE_COMMIT` to the checkout's current commit.

The header of each program records the Cake commit and a digest of the kernel
sources it came from.

## Performance

The tables give this kernel's device time in µs, from one profiled eager call
through vLLM's prefill indexer after warmup, without an L2 flush. A cell is
one request whose T new tokens end a context of L tokens. vLLM's default
512 MB logits budget splits a cell into launches of at most 512 MB of FP32
logits each; a time sums them. Speedups of the whole step compare CUPTI spans
of one indexer step captured in a CUDA graph, with L2 flushed before each
iteration.

### SM107

Measured on a Rubin GPU (200 SMs, SM clock capped at 1.73 GHz), so compare
relatively:

| new tokens | 32K context | 128K context | 1M context |
|---|---|---|---|
| 512 | 74.0 | 220.8 | 1707.3 |
| 2048 | 217.7 | 839.6 | 6787.4 |
| 8192 | 737.5 | 3260.3 | 26915.3 |

From 100M scored (row, key) pairs up, the kernel takes 3.1-3.3 ps per pair.
This CuTe DSL build (K = 32) is 1-4% slower than a CUDA C++ build with Rubin's
K = 64 MMA.

Through vLLM's indexer, with gvr_2, the whole prefill step is 1.18-1.29x
faster than DeepGEMM's MQA logits (with its schedule) + FP32 upcast + gvr_2,
and 1.17-1.35x faster with a 4096 MB logits budget. Its scores are FP32-exact
(top-2048 recall >= 0.9995 against FP32), while the DeepGEMM chain recalls at
least 97.7% of the exact top-2048. In memory, the step holds 1.0x the logits
budget, the DeepGEMM chain about 1.5x.

### SM103

Measured on a GB300 (152 SMs):

| new tokens | 32K context | 128K context | 1M context |
|---|---|---|---|
| 512 | 64.7 | 226.0 | 1760.6 |
| 2048 | 221.1 | 874.4 | 6996.9 |
| 8192 | 789.5 | 3448.6 | 30023.0 |

From 100M scored (row, key) pairs up, the kernel takes 3.3-3.5 ps per pair.

Through vLLM's indexer on the same GPU, the whole prefill step is 1.08-1.20x
faster than the DeepGEMM chain, with FP32-exact scores. The chain recalls at
least 98.1% of the exact top-2048.

## Tests

`tests/experimental/test_cake_fp8_ue8m0_paged_mqa_logits_prefill.py`: an FP32
reference over the cache bytes for cold prompts, appends after a cached
prefix, several requests, rows at tile edges and a 200k prefix; unscored rows
and columns left untouched; a row-strided block table and a wider output; the
default output's pitch; bit-identity with `fp8_ue8m0_paged_mqa_logits_decode` on
4-row groups; the plan covering every (row, tile) pair once; the input checks.
