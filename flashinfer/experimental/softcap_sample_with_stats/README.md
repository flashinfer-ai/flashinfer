# SM90 softcap sampling with row statistics (experimental)

The experimental CuTe-DSL backend of `flashinfer.sampling.softcap_sample_with_stats`. It fuses
the post-`lm_head` tail of a diffusion LM decode step (DiffusionGemma) into one pass over the
logits. That step samples every canvas position of every request and feeds the probabilities into
a self-conditioning matmul:

| Output | Meaning (row `r`, temperature `t`, `x = tanh(logits / c) * c` in FP32) |
|---|---|
| `argmax` int64 `[R]` | argmax of `x`, lowest index on ties |
| `sample` int64 `[R]` | Gumbel-max draw `argmax(x / max(t, 1e-10) + g)`; `argmax` when `t == 0` |
| `entropy` fp32 `[R]` | entropy (nats) of `softmax(x / t)` |
| `probs` bf16 `[R, V]` | `softmax(x / t)` rounded to BF16 once |

## Contract

- SM90 (H100 / H200) only. `logits` is contiguous BF16 `[R, 262144]` with `1 <= R <= 65535`.
- `temperature` is FP32 `[N]` with `N | R`. Rows `[i R/N, (i+1) R/N)` use `temperature[i]`.
- `softcap` is in `[2^-16, 64]`.
- `seed` is an `int` in `[0, 2^32)` or an int64 CUDA tensor; for a tensor, element 0's low 32 bits are read on the device.

### RNG stream

Philox4x32-10 with key `(seed, 0)`. Column `c` of row `r` takes word `(r V + c) & 3` of the
call at counter `((r V + c) >> 2, 0, 0, 0)`, so one call serves four columns. A word becomes a
uniform `u` as in `tl.uint_to_uniform_float`, and `g = -log(-log(max(u, 1e-20)))`.

`tl.philox(seed, (r * V + c) >> 2, 0, 0, 0)` reproduces the stream, so a Triton fallback can
match it. The test does exactly that.

## Numerics

The kernel uses `tanh.approx`, `ex2.approx` and `lg2.approx`. Gumbel keys compare the ratio
`exp(y - ref) / -log2(u)` with the low 5 mantissa bits replaced by the column slot. Validated
bounds against a direct FP32 evaluation:
- every probability within 2 BF16 ulps;
- every row's L1 distance at most 1e-2;
- mean row L1 at most 1e-4, and |mean row-sum bias| at most 5e-5;
- entropy within `5e-4 + 1e-4 |ref|`;
- `argmax` / `sample` differ only at FP32 near-ties.

A per-request kernel recomputes the entropy of requests with `t < 0.25` using the
`tanh(z) = 1 - 2 / (1 + e^(2z))` form of the softcap (`ex2` + `rcp`). There a direct-tanh ulp is amplified by `1 / t`.
Reductions have a fixed order, so results are bitwise reproducible.

## Launch structure

1. **Cooperative main kernel.** Groups of 8 CTAs (one 1024-thread CTA per SM, 224 KB of shared
   memory) each own one row at a time.
   - The `8 * floor(#SMs / 8)` CTAs are all co-resident.
   - Each CTA reads its eighth of the row once, using `cp.async`, and keeps the exps in shared
     memory.
   - The 8 CTAs of a group exchange per-row partials through tagged 64-bit records in a global
     workspace.
   - It then writes the BF16 probabilities once.
2. **Helper kernel** (PDL; only when at least 4 SMs are left over, e.g. 132-SM parts). Four
   two-pass CTAs take a suffix of the rows on the idle SMs.
3. **Cold-entropy kernel** (PDL). One warp per temperature group; it exits at once unless
   `t < 0.25`.

**Workspace protocol.** The record of row iteration `it` is tagged `it + 1`. The CTA that
finishes last does three things:
- detects that it is last with an `acq_rel` completion counter in the workspace;
- zeroes every record;
- resets the counter.

Every launch therefore starts from a zeroed workspace:
- No host-side epoch is involved, and a captured launch replays correctly.
- Workspaces are cached per `(device, stream)`. Calls on one stream are ordered and share one;
  concurrent calls on different streams each get their own.

**CUDA graphs.** Everything runs on the current stream without host synchronization, and the
calls may be captured in a CUDA graph. With a tensor `seed`, updating the tensor in place gives
each replay fresh noise.

## Performance (H200, `bench_softcap_sample_with_stats.py`)

The baseline is the two-kernel Triton structure of vLLM's DiffusionGemma sampler: an FP32
softcap copy, then one CTA per row with two passes. It draws the same RNG stream.

| rows | Triton (ms) | FlashInfer (ms) | speedup |
|---:|---:|---:|---:|
| 256 | 0.745 | 0.125 | 5.95x |
| 512 | 1.447 | 0.238 | 6.08x |
| 1024 | 2.834 | 0.461 | 6.15x |
| 1536 | 4.206 | 0.693 | 6.07x |
| 4096 | 10.97 | 1.849 | 5.93x |

## Provenance

The kernels were generated by an NVIDIA Kernel Factory campaign: CuTe-DSL agents optimizing
against a Triton reference of this contract on H200. The selected candidate is
`kernels.py` (cooperative main, helper and cold-entropy kernels).

It was adapted for FlashInfer in four ways:
- the launches run on the caller's stream;
- a device-side completion counter and zero-on-exit release replace the host-side epoch
  counter of the original;
- the seed can be device-resident;
- the kernels use FlashInfer's persistent CuTe-DSL compile cache.

The original's fallback for softcaps outside `[2^-16, 64]` is not included.
