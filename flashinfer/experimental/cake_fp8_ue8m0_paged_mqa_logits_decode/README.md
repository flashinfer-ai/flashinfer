# Cake FP8 paged MQA decode logits over UE8M0-scaled keys (SM103, SM107)

Owner: @jdebache · Tracking issue: [#8019](https://github.com/flashinfer-ai/flashinfer/issues/8019) · Status: experimental, JIT-only

Experimental backend of `flashinfer.attn_scores.fp8_ue8m0_paged_mqa_logits_decode`:
the DSA indexer decode logits over an FP8 paged key cache whose per-token
scales are UE8M0 exponents, the indexer cache vLLM writes on SM100-family
GPUs, for the 32-head x 128 indexer geometry. Both the API and the backend are
experimental. Calling the API is the opt-in (it warns once with
`ExperimentalWarning`); it takes part in no automatic backend selection,
autotuning or trace-apply, and has no fallback.

## Entry point

```python
from flashinfer.attn_scores import fp8_ue8m0_paged_mqa_logits_decode

logits = fp8_ue8m0_paged_mqa_logits_decode(
    q,             # [B, next_n, 32, 128] float8_e4m3fn, next_n in {1, 2, 4}
    kv_fused,      # [num_blocks, 64, 1, 132] uint8
    weights,       # [B * next_n, 32] float32
    block_tables,  # [B, width] int32, unit column stride, any row stride
    seq_lens,      # [B] int32: the KV length the newest token of each request sees
    max_seq_len,   # >= max(seq_lens)
    out=None,      # optional float32 [>= B * next_n, >= max_seq_len], contiguous
)                  # -> float32 [B * next_n, max_seq_len], a view of out
```

Row `b * next_n + t` scores key `j <= seq_lens[b] - next_n + t` as

```
2^(e_j - 127) * sum_h weights[b * next_n + t, h] * relu(q[b, t, h, :] . k_j)
```

Each 64-token block of `kv_fused` holds the 64 x 128 E4M3 values
(token-major), then 64 four-byte scale slots; the kernel reads a token's
exponent `e_j` from the slot's first byte (vLLM repeats it in all four). Keys
past a row's visible length get -inf up to the end of the request's last
256-key tile; later columns, and the rows of zero-length requests, are not
written. All tensors must be 16-byte aligned. The checks read host metadata
only, so the call is safe to capture in a CUDA graph; lengths may change
between replays. The full contract is in the API docstring.

## Kernel

One CTA scores a contiguous range of 256-key tiles of one request against all
of the request's query tokens. The grid is `(B, max(1, num_SMs // B))`, and
each CTA derives its range from the request's length on the device. Roles:

- a Q warp: one TMA of the request's `next_n x 32` query rows;
- a KV warp: block-table entries, then per page a 3-D TMA of the 64 x 128 E4M3
  values and a 2-D TMA of the 64 x 4 scale bytes (five stages);
- an MMA warp: tcgen05 FP8 MMAs `D[128 keys, next_n x 32] = K . Q^T` with
  K = 32, one TMEM slab per math warpgroup;
- two math warpgroups: each key's TMEM row reduced to
  `sum_h w_h relu(acc_h)` in packed f32x2 FMAs, times `2^(e - 127)`, stored
  as fp32. The scale is positive, so `s relu(x) = relu(s x)` and it
  multiplies the reduced score once per key instead of entering the MMA.

## Layout of this package

- `backend.py`: the input checks, the JIT load, and the launch: the TMA
  descriptor dimensions and 16-byte strides the generated launcher takes,
  and the grid. On load it checks that each program's launcher takes exactly
  the parameters it binds.
- `../cake_fp8_ue8m0_paged_mqa_logits_common/`: shared with the prefill
  backend: the supported architectures, the generated-program loader and
  launcher check, and the launch-device guard.
- `csrc/dsa_indexer_decode_logits_n{1,2,4}_{sm_103a,sm_107a}.py`: CuTe DSL
  programs generated by Cake (loom's CuTe DSL backend), one per next_n and
  architecture. Do not edit them. They import only `cutlass`
  (nvidia-cutlass-dsl) and `cuda.bindings`, so neither loom nor Cake is
  needed at runtime. The programs of the two architectures differ only in
  the target they name. They are compiled on first use (about a second
  each, ptxas -O2) and cached by `flashinfer.jit.cute_dsl_core` under
  `$FLASHINFER_JIT_DIR/cake_fp8_ue8m0_paged_mqa_logits_decode_<arch>_cute_dsl/`.

Regeneration requires the separately maintained Weave kernel sources and
CAKE exporter; neither is a runtime dependency of this package. From that
source checkout, invoke its decode export entry point with
`<flashinfer>/flashinfer/experimental/cake_fp8_ue8m0_paged_mqa_logits_decode/csrc`
as the output directory, and set `CAKE_COMMIT` to the checkout's current commit.

Each program's header records the CAKE commit and a digest of the kernel
sources.

## Performance

All timings are the CUPTI span of one call captured in a CUDA graph, with L2
flushed before each iteration, in µs.

### SM107

Measured on a Rubin GPU (200 SMs, memory clock capped), so compare relatively:

| requests x keys | next_n 1 | next_n 4 | next_n 4, no stores (floor) |
|---|---|---|---|
| 1 x 128K | 10.0 | 12.5 | 12.4 |
| 32 x 128K | 75.7 | 95.7 | 78.7 |
| 32 x 1M | 509.8 | 639.6 | 503.2 |

The no-stores floor comes from the same kernel built through loom; this API
always stores. The scores are bit-identical to the same kernel built through
loom as CUDA C++ with the K = 32 MMA. That build is 0-4% faster with stores at
next_n 4 (616 vs 640 µs at 32 x 1M) and at parity otherwise. The gap to the
floor is the fp32 stores: 512 MiB at 32 x 1M next_n 4.

In vLLM's sparse indexer decode op, this kernel with FlashInfer's
`top_k_varlen` gvr_2 top-k is 1.15-1.70x faster than vLLM's DeepGEMM bf16
chain, and exact in fp32. It is 2.4x faster at 32 x 1M next_n 4, where vLLM's
persistent top-k hits its data-dependent slow case. The chain recalls
98.2-99.3% of the exact top-2048. That was measured on a 216-SM Rubin GPU.

### SM103

Measured on a GB300 (152 SMs). The fastest streaming read measured on such a
GPU is 6.77 TB/s; the last column divides the key bytes read (132 per key)
by it.

| requests x keys | next_n 1 | next_n 2 | next_n 4 | key read at 6.77 TB/s |
|---|---|---|---|---|
| 1 x 128K | 8.4 | 8.6 | 10.2 | 2.6 |
| 32 x 128K | 102.6 | 105.3 | 121.7 | 81.7 |
| 32 x 1M | 730.9 | 751.5 | 847.4 | 653.9 |

At 32 x 1M the kernel moves 6.2 TB/s of key reads and logit writes at
next_n 1 and 5.9 TB/s at next_n 4.

In vLLM's sparse indexer decode op on the same GPU, this kernel with gvr_2 is
1.11-1.64x faster than vLLM's default chain (DeepGEMM's logits and vLLM's
top-k), and 2.2x faster at 32 x 1M next_n 4. The logits alone account for
1.04-1.26x. The top-k is exact, and the default chain recalls 98.2-99.3% of
it.

## Limitations

- Compute capability 10.3 and 10.7, the architectures the programs are
  generated and validated for. SM100 would need programs exported for
  sm_100a, and validation on that hardware.
- num_heads 32, head_dim 128, block_size 64, next_n in {1, 2, 4}. The CuTe
  DSL backend lowers the FP8 MMA at N = 32, 64 and 128, not at N = 96
  (next_n 3).
- K = 32 MMA, SM103's only dense FP8 MMA. On SM107, the CuTe DSL backend
  lowers Rubin's K = 64 FP8 MMA only in its block-scaled form. K = 64 would
  save about 1.5 µs at the smallest shapes (1 x 128K) and nothing at large
  ones.
- Unchecked preconditions, since checking would read device memory: each
  request's block-table entries index `kv_fused`, and
  `max(seq_lens) <= max_seq_len`. A longer request is truncated at the
  output's column count, never written out of bounds.

## Tests

`tests/experimental/test_cake_fp8_ue8m0_paged_mqa_logits_decode.py`:
- an fp32 reference over the cache bytes for next_n 1, 2 and 4, including
  zero-length and one-key requests and more requests than SMs;
- the -inf and unwritten columns;
- a row-strided per-token block table and a wider caller-owned output;
- CUDA-graph replay with changed lengths;
- agreement with `fp8_paged_mqa_logits` on the same keys with fp32 scales,
  within 1e-4 relative (the two kernels sum the heads in different orders);
- the input checks.
