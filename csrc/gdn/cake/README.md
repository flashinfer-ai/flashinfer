# Cake GDN non-CP prefill and decode source

Source-only CUDA kernels and TVM-FFI host shims for the FlashInfer GDN
non-CP prefill and decode backends on SM100a (B200), SM103a (B300) and
SM107a (Rubin R200).
The kernels were generated by Cake; the layout below is maintained by hand
with per-variant SASS equivalence checks against the generated originals.

## Layout

- `manifest.json` is the only registry. Each entry under `variants` names
  its kernel sources (`outputs[].path`, each shared by every specialization of
  the same kernel body), the `specializations` the resolver matches (also
  passed as the `-D` flags that specialize the body, unless the entry spells
  out its own `defines`: the decode bodies that bake their constants in-file
  take none, and some bodies take only a subset of the keys), and the
  template, kernel symbol and parameters of its host shim (`host_binding`).
  Five fields are not stored: `flashinfer/jit/cake_gdn.py` derives them when
  it loads the manifest, so the record name `<domain>_<schedule>_<12 hex>`
  is load-bearing for the resolver key. `domain` is its first token,
  `source_schedule` is `flashinfer.cake_gdn.generated.<domain>:<schedule>`,
  `tma_abi` is `grid_constant` for prefill and `pointer` for decode,
  `host_binding.entry` is `run_<name>`, and the record-level
  `architectures` is the sorted union of its outputs' `architectures`. An
  entry that spells one of these out must agree with the derived value; the
  loader refuses a disagreeing entry.
- `cuda/` holds one file per distinct kernel body. Kernels that run on
  several architectures carry each in `outputs[].architectures`; the
  outputs of a record are disjoint and their union is the record's derived
  `architectures`; the loader compiles the one output that lists the
  device's architecture. Genuine
  lowering differences sit behind exact `__CUDA_ARCH__` guards (SM107a takes
  the generic shared-address form, as Cake lowers it for every SM100-family
  target other than exact SM100a; the eight `fullgrid_vhold` prefill variants
  stay SM100a-only; a prefill body that SM107a shares with SM100a and/or
  SM103a masks its shared-memory descriptor addresses per architecture
  inside the one file -- the per-file `CAKE_GDN_SMEM_DESC_MASK`, `0x7FFF`
  under `#if __CUDA_ARCH__ == 1070` and `0x3FFF` otherwise, or an exact
  `#if __CUDA_ARCH__ == 1030` guard -- so no prefill record carries a
  mask-only SM107a copy of another body) or, when one architecture's
  lowering of a shared body
  differs from the shipped text, in that architecture's own output: the
  SM107a decode bodies scale q through `cake_f32_mul_f64const_rn` (an exact,
  FP64-free emulation of `(float)((double)x * SCALE)` defined in
  `cake_gdn_device_common.cuh`; Cake's generator names it
  `loom_f32_mul_f64const_rn` and the export maps the `loom_` prefix to
  `cake_`) and are delivered as `sm_107a`-only outputs of the same records,
  while the SM100a/SM103a outputs keep the shipped text byte for byte. In the
  manifest this reads as follows: a decode record exported for SM107a together
  with SM100a/SM103a (16 three-architecture decode records in the current
  manifest) keeps its shipped body as `outputs[0]` with `architectures`
  reduced to `["sm_100a", "sm_103a"]` and gains an `sm_107a` output; a decode
  record exported for SM107a alone (the `_vpre` / `_pro` bodies; the fp32 T=1
  `splitv8_tilev32` band body is born in this form) whose program takes the
  helper gets a replacement body and its old file leaves the tree; `cake_gdn_device_common.cuh` is re-rendered for all three
  architectures (it carries the helper definitions for every kernel that
  includes it; the current generator writes them as content-addressed
  `#include "cake_device_helpers/cake_<name>_<sha256[:16]>.cuh"` files under
  `csrc/`, shared with other Cake families, so the cubin compile adds `csrc`
  to its include path). No SM100a/SM103a kernel body and no kernel's
  behaviour changes.
  `../cake_gdn_common.cuh` is the shared device header of the decode bodies
  that do not include `cake_gdn_device_common.cuh`.
  In-file defines and the same values passed as `-D` are not interchangeable:
  for three prefill variants (`dvsplit_initial_bf16state_135bfa59984f`,
  `..._d8b5b50285af`, `dvsplit_initial_f16io_f481beb70ea9`) compiled from the
  shared body with their values passed as `-D`, nvcc 13.4 (sm_103a) schedules
  the kernel differently from the in-file form (same instruction count;
  register assignment, instruction order and one uniform address computation
  change), deterministically.
- `host/templates/` holds one TVM-FFI launcher template per shim class. The
  former per-variant shims differed only in identifiers and literals, which
  the templates take as `@NAME@` placeholders: `@ENTRY@`, `@MODULE_IDENT@`,
  `@CUDA_SYMBOL@` and `@SHIM_NAMESPACE@` come from `host_binding` (`entry`,
  `module_ident`, `cuda_symbol`, `shim_namespace`), every other placeholder
  from `host_binding.params`. A `//@if metadata_i64` / `//@else` / `//@endif`
  block of lines keeps its first arm for a record whose `metadata_i64` is true
  and its second arm otherwise, so the int32-or-int64 metadata checks of the
  SM107a prefill records render from their base's template; the directive
  lines are dropped. `flashinfer/jit/cake_gdn.py` renders the shim
  text at load time; `tests/cpu/gdn/cake_gdn_host_shim_sha256.json` pins
  the rendered text per variant. The helpers the launchers share
  (device guard, tensor checks, the `EncodeTma3D` TMA encoder, dynamic
  shared-memory opt-in) live in `host/cake_gdn_host_common.h`.

`flashinfer/jit/cake_gdn.py` compiles the kernel to a cubin with `nvcc`,
embeds it into the rendered host shim, and resolves requests to exactly one
listed variant; requests outside the listed routes fail closed.

Two more body-sharing `-D` knobs join `CAKE_GDN_KERNEL_SYMBOL` and `LAUNCH_MIN_BLOCKS`:
`CAKE_GDN_METADATA_I64` (default 0 in-file) selects, inside the eight shared prefill bodies, the int32-or-int64 reads of
`cu_seqlens` / `state_indices` / `checkpoint_cu_starts` and the `int metadata_i64_mask` kernel parameter (after `total_tiles`)
(`CAKE_GDN_METADATA_I64_PARAM`); the SM107a `metadata_i64` records pass `-DCAKE_GDN_METADATA_I64=1` and their own
kernel symbol and compile the same body as their SM100a/SM103a base record.  `CAKE_GDN_FP8_X2` (default `e4m3x2`)
names the FP8 pair type inside the `cvt` instructions of the FP8-state bodies; the e5m2 records pass
`-DCAKE_GDN_FP8_X2=e5m2x2`.  Expanding a shared body with a record's defines reproduces the former per-record file
token for token (the e5m2 arm up to the names of a few local variables), under the per-variant SASS equivalence checks against the generated originals.

## Contracts

Indexed prefill requires every state slot to be in `[0, pool_size)`.
Indexed decode requires every initial/output state slot to be `-1` or in
`[0, state.size(0))`. Both adapters trust caller-provided slots by default
(parity with the CuTe kernels) and perform an asynchronous fail-closed check
on the caller stream (device-side assert, also under CUDA Graph capture and
replay) only when `FLASHINFER_CAKE_GDN_VALIDATE_SLOTS=1`.

### Non-CP prefill: host-free launch

The non-CP prefill route (`flashinfer/gdn_prefill.py::_run_cake_gdn_prefill`,
`backend="cake_gdn"` with `use_cp=False`/`"auto"`) reads nothing back from
the device. There is no host-int cache, no cached int32 copy and no
capture-time "warm up eagerly first" error; the one-time `nvcc` compile and
TVM-FFI load of a kernel variant is the only eager step before a CUDA Graph
capture.

- Host-known inputs. `num_seqs = cu_seqlens.numel() - 1` and
  `total_tokens = q.shape[0]` are shapes. The kernel variant
  (`flashinfer/jit/cake_gdn.py::select_cake_gdn_prefill_variant`, no
  `seq_lens` argument) and the persistent grid follow an upper bound on the
  longest sequence: the exact maximum from `cu_seqlens_cpu` when given, else
  the public `max_seqlen` hint, else `total_tokens`. A loose bound is always
  correct; it only changes the grid size and whether the stateless
  single-chunk kernel (bound <= 64 tokens, no initial/final state, no
  checkpoints) is eligible.
- `cu_seqlens_cpu` (keyword-only on `chunk_gated_delta_rule`): an optional
  host copy of `cu_seqlens` -- a one-dimensional int32/int64 CPU tensor or
  a sequence of Python ints of length `num_seqs + 1` with the same values
  (vLLM `query_start_loc_cpu`, the prefix sums of SGLang
  `extend_seq_lens_cpu`). With it the host validates the offsets
  (non-decreasing, first `0`, last `total_tokens`), rejects a `max_seqlen`
  smaller than the exact maximum and checks the checkpoint count exactly,
  all before any launch and without a synchronization. A CUDA tensor is
  refused, not copied. Other backends ignore the parameter.
- Device-side guard (kernel launch ABI v2). The kernel receives
  `total_tokens` as a scalar after `num_seqs` and resolves `cu_seqlens` per
  work tile: `begin = min(cu_seqlens[b], total_tokens)`,
  `end = min(max(cu_seqlens[b + 1], begin), total_tokens)`. Offsets past the
  token count are clamped and a non-monotonic pair becomes an empty sequence
  -- a documented no-op (its output rows are untouched, its state slot keeps
  the initial state), never an out-of-bounds access and never a trap. The
  consistency of `checkpoint_cu_starts` with `cu_seqlens` and the interval
  stays a caller precondition, as the public docstring states; the host does
  not read it.
- Grid rule (`_cake_gdn_prefill_grid_x(total_tiles, sm_count, dvsplit,
  bound_tokens)`, one formula shared with the Cake program's
  `_select_persistent_grid_ctas`): DV-split or `total_tiles <= 128` ->
  `min(sm_count, total_tiles)`; else `G = min(sm_count, total_tiles)` when
  `ceil(total_tiles / G) < ceil(total_tiles / 128)`, otherwise `128` (ties
  keep 128). `bound_tokens` is validated but does not change the grid.
  The host shim checks `0 < grid_x <= total_tiles` and the tensor-map
  workspace size (`512` bytes per CTA, cached per device, stream and grid).
- Metadata dtypes. A record whose manifest entry carries
  `"metadata_i64": true` (every sm_107a non-CP prefill record; the field is
  absent elsewhere) reads int32 or int64 `cu_seqlens`, `state_indices` and
  `checkpoint_cu_starts` directly: its host shim accepts either width for
  the three buffers, derives the kernel's trailing `metadata_i64_mask`
  scalar from their dtypes (bit 0 / 1 / 2 = `cu_seqlens` / `state_indices`
  / `checkpoint_cu_starts` is int64) and the TVM-FFI entry signature is
  unchanged; int32 and int64 metadata are both zero-copy there
  (`CakeGDNRoute.metadata_i64`). Every other record takes int32 offsets
  and slots: int32 metadata reaches the kernel as is (zero-copy path) and
  int64 metadata is cast on the caller's stream at every call (one small
  device kernel, recorded into the graph under capture). Nothing is cached
  by tensor identity, so a buffer rewritten in place -- an inference-mode
  tensor without a version counter, a persistent engine buffer, or the
  inputs of a captured graph between replays -- is always what the kernel
  reads.
- CUDA Graph. Capture needs no prior eager call for the same metadata; replay
  reads the live `cu_seqlens`, `state_indices`, `checkpoint_cu_starts` and
  data buffers. Tests: `tests/gdn/test_cake_gdn_prefill_gpu.py` (zero-sync
  proof under `torch.cuda.set_sync_debug_mode("error")` plus a profiler
  check, cold capture, in-place rewrite replay, chunked state carry, int64 /
  int32 equivalence per buffer and mixed widths -- zero-copy and one kernel
  per call on a `metadata_i64` record -- malformed-metadata no-op) and the
  CPU contract tests in `tests/gdn/test_cake_gdn_prefill.py`.

Use the GDN prefill API with `backend="cake_gdn"` to select this backend
explicitly; automatic prefill dispatch continues to select CuTe.  Under
`backend="cake_gdn"` with `use_cp="auto"` (the default), a BF16/FP16-I/O row
with FP32 initial + final state, gates, no checkpoints and no state indices
whose work leaves most SMs idle (`4 * num_seqs * max(Hq, Hv) < SMs`) and whose
longest sequence (`max_seqlen`) has at least 4096 tokens runs the Cake CP
backend (`csrc/gdn/gdn_cp`, `flashinfer/gdn_kernels/blackwell/cake_gdn_cp_backend.py`)
on SM100a/SM103a instead of a record of this manifest; every other row keeps
the non-CP record.  Pass `max_seqlen` when the batch has more than one
sequence: without it the band estimates the longest sequence as `ceil(total_seq_len / num_seqs)` (the Cake CP
program's convention for an omitted hint), which matches the Cake dispatcher only for balanced batches.
Decode requests with `backend="auto"` try the listed decode variants first.

The decode variants include the Qwen3.5-35B-A3B TP=2 speculative-verify
rows (H=8 / HV=16, BF16 state pool, seven-step BF16 checkpoint cache,
`disable_state_update=True`): `gdn_decode_pretranspose_t4_bf16state_tile16`
specialized to `T_STEPS=7` and `T_STEPS=8` for B<=4 and
`gdn_decode_pretranspose_mtp_t4_bf16state_wide128` with `T_STEPS=7`,
`TILE_V_WIDE=32` for B>=5 (H=8/HV=16) and TP=1 (H=16/HV=32).
On SM107a (Rubin R200) the tile16 rows (and the Qwen3-Next TP=4 H=4/HV=8
T=4 rows) resolve to `gdn_decode_pretranspose_t4_bf16state_tile16_vpre`
instead: the same kernel contract and arithmetic (bitwise-identical output)
with every draft token's v values staged in shared memory ahead of the serial
recurrence and the token loop unrolled; its records are exported for `sm_107a`
only, while SM100a/SM103a keep the shipped tile16 body
(`cake_gdn_bf16_verify_tile16_schedule` in `flashinfer/jit/cake_gdn.py`).
The same two schedule changes are applied to the wide multi-token body on
SM107a: every other BF16-state T>=2 row (verify / update / checkpoint flavours
at `TILE_V_WIDE` 32 and 64, including the TP=2 B>=5 and TP=1 verify rows)
resolves to `gdn_decode_pretranspose_mtp_t4_bf16state_wide128_vpre` there
(`cake_gdn_bf16_wide_schedule`), again bitwise-identical to the shipped body;
the single-token band rows keep `..._wide128` on every architecture.
The promoted fp32-state MTP update row (B=4 T=4 with the intermediate-state
cache) resolves on SM107a to `gdn_decode_pretranspose_mtp_t4_splitv8_pro`
(`CAKE_GDN_FP32_MTP_ARCH_BODIES`): the producer phase runs one warp per draft
token and every independent global load is issued before the first reduction;
bitwise-identical to the shipped body, which SM100a/SM103a keep.  The fp32
verify row (B=1 T=2, `..._mtp_t2_inline_tile8`) keeps one body everywhere.
The indexed fp32-state T=1 row (`gdn_decode_pretranspose_splitv8`, H=16 /
HV=32) follows the state-head count `B * HV` on SM107a
(`CAKE_GDN_FP32_T1_SPLITV8_ARCH_BANDS`, `cake_gdn_fp32_t1_route`): below 256
state heads the shipped `splitv8` body (TILE_V 16, eight CTAs per state head),
from 256 on its `gdn_decode_pretranspose_splitv8_tilev32` twin (TILE_V 32,
four CTAs per state head; bitwise-identical output, only the row -> CTA
mapping changes), 5-8.5 % faster on R200 from 256 through 2048 state heads
under the route id `..._indexed_fp32_t1_splitv8_tilev32`.  Its records are
exported for `sm_107a` only; SM100a/SM103a keep `splitv8` at every count.  The
host launches `B * HV` times the CTAs per state head of the resolved record
(`cake_gdn_fp32_t1_ctas_per_state`, keyed by the record's schedule), and each
shim checks that grid.

Single-token BF16-state decode admits every Qwen3.5 per-rank linear-attention
geometry at any batch: H/HV = 16/32, 8/16, 4/8 (Qwen3.5-35B-A3B TP1/TP2/TP4)
and 8/32, 4/16, 2/8 (Qwen3.5-397B-A17B TP2/TP4/TP8). The resolver picks the
body and grid tile from the state-head count `B * HV`
(`cake_gdn_bf16_t1_route`): up to 768 state heads one of two launch-bound
instances of `gdn_decode_pretranspose_t1_bf16state_vec8` -- eight 16-lane
groups per CTA, one 16-byte load per lane and state row, `TILE_V` 16 / 32 /
64 -- where the `vec8` instance (`__launch_bounds__(128, 1)`) issues every
first-block load ahead of the Q/K normalization for the latency-bound small
pools (on sm_103a the 9-192 state-head band takes the `vec8r56` instance,
`__launch_bounds__(128, 9)`, a 56-register cap that keeps the hoisted
schedule at `TILE_V` 16 without spills and runs 1.4-4.3 % faster there, while
the sm_100a build of the cap is slower and B200 keeps `vec8`), and the
`vec8occ` instance (default launch bounds, eight CTAs per SM)
takes the 256- and 512-head bands whose 1024-CTA grids then run in a single
wave; above 768 state heads the MTP wide-tile body
`gdn_decode_pretranspose_mtp_t4_bf16state_wide128` at `T_STEPS=1`,
`TILE_V_WIDE=128` (one CTA per state head) streams the bandwidth-bound pools.
The route id carries the body and tile and the host launches
`B * HV * 128 / tile_v` CTAs. Every body reads its input strides at runtime,
so packed SGLang QKV views and contiguous tensors share one variant. An
unlisted (geometry, body, tile) triple fails closed.

The BF16-I/O + BF16-state prefill kernels (`..._dvsplit_initial_bf16state`
and the full-DV `..._initial_bf16state`, gathered state, no checkpoints)
are specialized for the same per-rank head splits:
`HEAD_GROUP_LOG2`/`NUM_O_HEADS_LOG2` = 1/4, 1/3, 2/5, 2/4 and 2/3.
